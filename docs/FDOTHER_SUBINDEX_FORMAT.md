# FDOTHER.DAT 서브인덱스 포맷 업데이트 분석

## 실제 관측된 데이터 구조

### 타입 A: 서브항목 없음 (sub_count = 0)
- 예시: 인덱스 18 (16x16)
```
바이트 0-1: width (리틀 엔디언)
바이트 2-3: height (리틀 엔디언)
바이트 4+:   RLE 데이터 스트림
```

### 타입 B: 서브항목 있음 (sub_count > 0)
- 예시: 인덱스 1 (24x24, 20개 서브항목), 인덱스 19 (30x30, 30개 서브항목)
```
바이트 0-1:   width (리틀 엔디언)
바이트 2-3:   height (리틀 엔디언)
바이트 4-5:   sub_count (리틀 엔디언, 서브항목 수)
바이트 6+:    offset_table (항목당 4바이트 DWORD, 상대 오프셋)
             - 오프셋은 "서브항목 데이터 블록 시작 위치" 또는 "주 리소스 시작 위치" 기준
바이트 N+:    RLE 데이터 스트림 (offset 테이블 종료 후)
```

### 핵심 문제
offset 테이블이 가리키는 위치는 RLE 이미지 데이터가 아닌 **중간 포맷** 또는 **참조**입니다.

offset 위치에서 읽은 처음 2바이트는 주로:
- 0x81XX 또는 기타 RLE 명령값
- 유효한 width 값이 아님

## 인덱스 18 상세 분석

```
바이트 0-1:   0x10 0x00 -> width = 16
바이트 2-3:   0x10 0x00 -> height = 16
바이트 4-7:   0x00 0x00 0x00 0x00 -> offset[0] = 0?
바이트 8-11:  0x48 0x00 0x00 0x00 -> offset[1] = 0x48 = 72
바이트 12-15: 0x6D 0x00 0x00 0x00 -> offset[2] = 0x6D = 109
...
```

바이트 72의 데이터: `0A 00 00 00 00 00 00 00 01 00 0C 00 80 97...`
- 이것이 RLE 헤더라면: width = 10, height = 0 (유효하지 않음)

## 가능한 해석

1. **offset 테이블이 중첩된 서브 리소스를 가리킬 수 있음**
2. **실제 RLE 데이터는 offset 테이블 이후**(바이트 86부터 시작)에 위치하며, offset 테이블은 임의 접근 기능만 제공
3. **FDOTHER 리소스에 여러 변형 포맷이 있을 수 있음**

## 인덱스 1의 offset 테이블 분석

| 인덱스 | 오프셋 (hex) | 가리키는 데이터 |
|--------|-------------|----------------|
| 0 | 0x56 | 8160be04bd82... |
| 1 | 0x133 | 8160be04bd88... |
| 2 | 0x22e | 8160be04bd88... |
| ... | ... | ... |

모든 offset 위치의 데이터는 `81` 또는 `82` 등의 RLE 명령 바이트로 시작합니다.
